브라우저 격투 게임을 서버 중계에서 P2P로 옮긴 이유

작성 2026-11-24 · catchmeif404

마스크맨은 브라우저에서 하는 1대1 격투 게임이에요. 두 사람이 네 글자 방 코드로 들어오면, 방마다 하나씩 있는 Cloudflare Durable Object가 둘을 이어 줘요. 첫 버전은 대전 중 입력도 전부 이 방을 거쳐서 보냈어요. 동작은 했지만 게임이 되지 않았어요.

한국에서 서버 중계는 너무 느렸어요

온라인 대전은 입력 락스텝 방식이에요. 양쪽이 프레임마다 버튼 비트만 보내고, 각자 같은 시뮬레이션을 돌려요. 그 외에는 네트워크로 오가는 게 없어요. 그러니 입력이 몇 프레임 안에 도착해야 해요. 한 프레임은 1/60초, 약 16.7ms예요.

2026-11-13에 v0.1.0을 실측해 보니, 한국에서 접속하면 Cloudflare 무료 플랜이 연결을 로스앤젤레스(LAX)로 보냈어요. 방을 거친 입력 지연은 330~1,400ms였어요. 초당 60프레임으로 치면 20~85프레임이라 다른 게임이 돼요. 어느 지역으로 가는지는 curl -s https://maskman.catchmeif404.com/cdn-cgi/trace | grep colo로 확인할 수 있어요.

같은 나라에 있는 두 사람의 입력이 태평양을 두 번 건널 이유는 없어요. 그래서 대전 트래픽을 서버를 거치지 않게 바꿨어요.

방 서버는 이제 연결만 맡아요

v0.2.0부터 방 서버는 시그널링만 해요. 두 사람이 준비되면 좌석, 설정, 스테이지가 담긴 Start 메시지를 보내요. 그다음 두 브라우저가 방을 통해 WebRTC의 offer, answer, ICE 후보를 주고받아요. 메시지 종류는 세 가지예요.

export enum SignalKind {
  Offer = 'offer',
  Answer = 'answer',
  Ice = 'ice',
}

데이터 채널이 열리면 입력 비트가 브라우저에서 브라우저로 바로 가요. 방 서버는 웹소켓을 계속 들고 있어서, 상대가 나갔다는 소식은 여전히 전해 줘요.

채널은 양쪽에서 같은 id로 만들어서 따로 협상할 필요가 없고, 순서는 보장하지 않지만 신뢰성은 있는 방식이에요.

this.dc = this.pc.createDataChannel('game',
  { negotiated: true, id: 0, ordered: false });

입력은 하나도 빠지지 않고 도착하지만, 늦은 패킷 하나가 새 패킷을 막지 않아요. 프레임 단위로 묶어 보내는 입력에는 이쪽이 맞는 선택이었어요. 공인 주소를 알아내는 데는 Cloudflare와 Google의 무료 STUN 서버 두 곳을 써요. 이 서버들은 바깥에서 내가 어떻게 보이는지만 알려 줘요.

측정한 경로로 입력 지연을 정해요

호스트는 열려 있는 경로로 핑을 다섯 번 보내고, 왕복 시간의 75번째 백분위를 프레임으로 바꿔요.

const frames = Math.ceil(rttMs / 2 / FRAME_MS) + DELAY_MARGIN;
return Math.min(MAX_DELAY, Math.max(MIN_DELAY, frames));

왕복의 절반을 프레임으로 환산하고 여유 2프레임을 더한 뒤, 3~15프레임 범위로 자르는 식이에요. 호스트가 이 값을 Go 메시지로 게스트에게 보내서 두 쪽이 같은 지연으로 경기를 해요. 개발 빌드에서는 window.stickDuel.net()으로 직접 연결 여부, 왕복 시간, 정해진 지연을 볼 수 있어요.

서버 중계 대체 경로와 그 한계

어떤 망에서는 직접 연결이 끝내 안 돼요. 일부 회사망이나 통신사 망이 그래요. 호스트는 데이터 채널이 열리기를 5초 기다리고, 열리지 않으면 웹소켓으로 지연을 재서 예전처럼 방을 거쳐 경기해요.

모든 전송은 한 함수를 지나가요. 데이터 채널이 열려 있으면 거기로 보내고, 아니면 소켓으로 보내요.

if (!this.path.send(text) && this.ws.readyState === WebSocket.OPEN)
  this.ws.send(text);

이 대체 경로 덕분에 연결과 동기화는 되지만 속도는 예전 그대로예요. 한국에서는 입력 지연이 크다는 뜻이에요. 해결책은 직접 연결이 안 되는 상대끼리 트래픽을 대신 넘겨 주는 TURN 서버인데, 아직 추가하지 않았어요. 그런 플레이어에게는 예전 지연이 그대로 남아 있어요.

아직 재 보지 않은 것

우리에게 있는 건 v0.1.0 중계 실측값과 직접 경로의 구조예요. 실제 여러 망에서 잰 직접 경로의 왕복 시간은 없고, 얼마나 자주 대체 경로로 떨어지는지도 재지 않았어요. P2P가 어디서나 충분히 빠르다고 말하려면 이 두 가지를 먼저 모아야 해요.
