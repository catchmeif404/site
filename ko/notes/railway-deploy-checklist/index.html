실패에서 나온 Railway 배포 체크리스트

작성 2026-11-24 · catchmeif404

우리는 태그로 실행되는 GitHub Actions 워크플로에서 railway up을 실행해 백엔드를 Railway에 배포해요. 이 구성에서 시간을 잃은 일은 대부분 작은 불일치 다섯 가지에서 나왔고, 그중 둘은 두 번 이상 겪었어요. 새 서비스를 만들 때, 또는 배포는 되는데 502가 나거나 Postgres를 못 찾을 때 이 체크리스트를 써요.

1. 서비스 이름이 --service와 정확히 같아야 해요

증상: 워크플로가 서비스를 찾지 못하거나, 의도하지 않은 곳에 배포돼요.

원인: Railway가 서비스 이름을 저장소나 폴더 이름으로 짓는다는 보장은 없어요. aws-cost-calculator의 백엔드 서비스 이름은 backend가 아니라 말 그대로 aws-cost-calculator예요.

해결: 대시보드에서 이름을 읽고, 그 문자열을 워크플로에 그대로 넣어요.

railway up --service aws-cost-calculator

2. railway up은 저장소 루트에서 실행해요

증상: "Root directory '/backend' was not found in the deployed source" 또는 "Railpack could not determine how to build the app" 오류로 빌드가 실패해요.

원인: 서비스는 두 가지 경로로 배포될 수 있어요. 워크플로로 올리는 경우와, 대시보드나 GitHub 연동으로 올리는 경우(수동 Deploy 클릭, 또는 아직 켜져 있는 Automatic Deploy)예요. 두 경로가 같은 모양의 소스를 올리지 않으면 Root Directory 설정은 둘 중 하나에만 맞을 수 있어요.

  • backend/ 안에서 railway up을 실행하면 이미 그 폴더로 좁혀진 스냅샷이 올라가요. 이때 Root Directory를 backend로 두면 이중으로 좁혀져 실패해요.
  • Root Directory를 비워 두고 대시보드 경로로 배포하면 Railpack이 저장소 루트를 훑고, 빌드할 진입점을 못 찾아 실패해요.
  • 저장소 루트에서 railway up을 실행하면 저장소 전체가 올라가서 대시보드 경로와 같아지고, Root Directory backend가 두 경로 모두에서 맞게 해석돼요.

해결: 배포 단계에 working-directory: backend도 defaults.run.working-directory도 두지 않고, Root Directory는 backend로 설정해요. 이 오류가 다시 나오면 Root Directory를 만지기 전에 워크플로가 다시 backend/ 안에서 실행되도록 바뀌지 않았는지 먼저 봐요.

3. 네트워킹 포트가 앱이 실제로 쓰는 포트와 같아야 해요

증상: 로그에는 앱이 떴다고 나오는데 모든 요청이 502 "Application failed to respond"를 돌려줘요.

원인: Railway는 자체 PORT 변수를 주입하는데 값이 8080인 경우가 많고, 앱은 Dockerfile의 EXPOSE와 상관없이 그 값에 바인딩해요. 생성된 도메인이 다른 포트를 가리키면 프록시가 앱에 닿지 못해요.

해결: 프레임워크가 시작할 때 남기는 로그 줄(Spring Boot라면 "Tomcat initialized with port ___")에서 포트를 확인하고, 도메인의 대상 포트를 그 값으로 맞춰요. 아니면 PORT를 변수로 직접 지정해 값을 고정해도 돼요.

4. Automatic Deploy를 끄고, 정말 꺼졌는지 확인해요

증상: 상관없는 기능을 작업하는 동안 무작위 실패가 나고 인스턴스가 낡아 보여요. 배포 방식 자체가 불안정해 보여요.

원인: Automatic Deploy(Settings, Source)를 껐다고 믿었지만 꺼져 있지 않았어요. main에 푸시할 때마다 Railway의 GitHub 연동이 두 번째 배포를 시작했고, 태그로 실행되는 railway up 워크플로와 경쟁했어요. aws-cost-calculator에서 디버깅에 긴 시간을 썼어요.

해결과 확인: 끈 뒤에, 마지막 배포를 무엇이 시작했는지 Railway에 물어봐요.

railway status --json

서비스의 latestDeployment.meta를 봐요. reason이 "deploy"이고 repo와 commitHash가 태그가 아니라 최근 브랜치 푸시와 일치하면 Automatic Deploy가 아직 동작하는 거예요.

5. 새 변수는 대시보드에서 배포하기 전까지 적용되지 않을 수 있어요

증상: 변수를 추가하고 워크플로를 여러 번 다시 돌려도 앱에서는 빈 값으로 보여요.

원인: ADMIN_METRICS_API_KEY를 추가하고 태그로 실행되는 railway up 워크플로를 계속 다시 돌렸어요. 값의 길이만 찍는 임시 디버그 로그로 보니 Railway에는 실제 값이 들어 있는데 앱은 ""를 보고 있었어요. Railway 대시보드에서 직접 Deploy를 한 번 누르자 비로소 적용됐고, 그 뒤로는 CLI로 시작한 재배포도 모두 정상이었어요.

해결: 변수를 추가하거나 바꾼 뒤에는 대시보드에서 Deploy를 한 번 눌러요. 그다음부터는 CLI 재배포를 믿어도 돼요. 이런 변수를 디버깅할 때는 값이 아니라 길이만 로그로 남겨요.

확인 순서

배포는 됐는데 응답이 없으면 서비스 이름, 소스 모양과 Root Directory, 포트, 두 번째 배포가 도는지, 마지막으로 변수 순서로 봐요. 앞의 네 가지는 대시보드나 railway status --json으로 읽을 수 있는 설정이라 빨리 배제할 수 있어요. 이 체크의 바탕이 되는 태그 기반 구성은 main이 아니라 태그로 배포해요에 적었어요.
