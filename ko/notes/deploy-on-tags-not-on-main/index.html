main이 아니라 태그로 배포해요

작성 2026-11-24 · catchmeif404

일부 저장소에서는 한동안 main에 머지하는 일과 운영에 배포하는 일이 같은 동작이었어요. 다른 기능을 만지는 중에도 푸시할 때마다 사용자가 쓰는 서비스가 바뀌니 불편했어요. 그래서 버전 태그를 푸시할 때만 운영이 바뀌도록 규칙을 바꿨어요.

규칙

main에 커밋하고 푸시하는 것만으로는 운영 배포가 일어나지 않아요. 배포는 vX.Y.Z 형식의 태그(semver, 예: v1.0.0)를 푸시할 때만 일어나요. 배포 워크플로는 태그를 트리거로 쓰고, 재실행을 위해 수동 실행도 열어 둬요.

on:
  push:
    tags: ['v*']
  workflow_dispatch:

릴리스는 main이 내보낼 상태인지 확인한 뒤 명령 두 줄이면 끝나요.

git tag v1.0.0
git push origin v1.0.0

프론트엔드와 백엔드가 같은 태그를 써요

기본은 저장소마다 태그 하나를 공유하고, 그 태그가 배포 가능한 모든 서비스의 워크플로를 실행하는 방식이에요. AWS CostPilot(저장소 이름 aws-cost-calculator)은 프론트엔드를 Cloudflare Workers에, 백엔드를 Railway에 배포해요. deploy-frontend.yml과 deploy-backend.yml이 같은 v* 태그로 실행되기 때문에 한 릴리스의 두 부분은 늘 같은 커밋에서 나와요.

서비스마다 frontend-v1.0.0, worker-v1.0.0 같은 접두어 태그를 따로 쓰는 방법도 있어요. 서비스끼리 독립적으로 릴리스해야 할 때만 이 방법을 써요. API 규약을 함께 쓰는 프론트엔드와 백엔드라면 태그 하나가 더 단순하고, 버전이 어긋나는 문제도 줄어요.

실제로 달라진 점

바꾸면서 가장 먼저 한 일은 배포 경로를 하나로 만드는 것이었어요.

AWS CostPilot 백엔드는 예전에 Railway의 GitHub 연동으로 main에 푸시할 때마다 자동 배포됐어요. 그 기능을 Railway 대시보드에서 끄고, Railway CLI로 railway up을 실행하는 태그 트리거 워크플로로 바꿨어요. 이 워크플로에는 Railway 프로젝트 토큰인 RAILWAY_TOKEN 저장소 시크릿이 필요해요.

일상에서는 이렇게 달라졌어요.

  • 풀 리퀘스트는 언제 머지해도 안전해요. 바뀌는 건 main이지 운영이 아니에요.
  • 작업 중인 기능이 여러 번의 머지에 걸쳐 main에 있다가 나중에 한 번에 릴리스될 수 있어요.
  • 배포에 이름이 생겨요. 태그를 보면 어떤 커밋이 운영 중인지 알 수 있고, 이전 태그를 수동 실행으로 다시 돌리면 이전 상태로 돌아갈 수 있어요.
  • 배포는 머지의 부수 효과가 아니라 의도해서 하는 단계가 돼요.

커밋과 풀 리퀘스트를 쓰는 방식에도 영향이 있었어요. 머지해도 배포되지 않으니, 덜 끝난 변경을 작은 단계로 먼저 넣어 두어도 이미 운영에 나갔을까 걱정하지 않아도 돼요. 지금의 main이 내보내도 될 상태인지는 풀 리퀘스트 하나하나가 아니라 main 전체를 보고, 태그를 찍는 시점에 한 번 판단해요. 데이터베이스 마이그레이션이 들어간 릴리스처럼 신중하게 내보내고 싶은 변경을 점검하는 시점도 바로 이때예요.

깔끔하게 적용되지 않은 두 곳

첫째는 catchmeif404.com 정적 사이트예요. Cloudflare Pages의 자체 git 연동으로 배포하고, main에 푸시할 때마다 다시 배포돼요. 순수 HTML, CSS, JavaScript라서 빌드 명령도 출력 폴더도 없어요. 이 사이트를 Actions 기반의 태그 배포로 옮기는 건 따로 해야 할 작업이고 아직 하지 않았어요. 태그 규칙은 모든 저장소가 가려는 방향이지, 이미 다 그렇다는 뜻이 아니에요.

둘째는 배포 방식을 껐다고 믿기는 쉽지만 확인하기는 어렵다는 점이에요. 백엔드에서 Railway 자동 배포를 껐다고 생각했는데, main에 푸시할 때마다 두 번째 배포가 시작돼 태그 워크플로와 경쟁하고 있었어요. 확인하는 방법은 Railway 배포 체크리스트에 적었어요.

기존 저장소를 옮길 때

main에서 배포하던 저장소를 만지게 되면 매번 같은 순서로 해요.

  1. 워크플로 트리거를 push: branches: [main]에서 push: tags: ['v*']로 바꾸고 workflow_dispatch를 추가해요.
  2. 호스팅 서비스 자체의 git 기반 배포를 꺼서 운영으로 가는 길을 하나로 만들어요.
  3. 토글을 눌렀다는 사실이 아니라 정말 꺼졌는지를 확인해요.
  4. 태그를 푸시하고 워크플로를 지켜본 뒤, 실제 주소를 열어 무엇이 돌고 있는지 확인해요.

마지막 단계도 앞의 세 단계만큼 중요해요. 태그를 푸시해서 워크플로가 초록색이 됐다는 건 워크플로가 돌았다는 증거일 뿐, 서비스가 바뀌었다는 증거는 아니에요. 이 이야기는 README가 아니라 배포를 확인해요에서 따로 다뤘어요.
