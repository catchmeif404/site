Running a Secret Santa without accounts

Published 2026-11-24 · catchmeif404

A Secret Santa is a small, short-lived group activity. Asking twelve coworkers to create accounts, confirm emails and remember passwords for one December exchange is a good way to lose half of them. We built SantaPick (santapick.catchmeif404.com) with no login at all. That leaves two questions: how does the server know who is asking, and how does it keep the one secret the whole game depends on, who gives to whom?

Two kinds of link

Access comes in two shapes, and they do different jobs.

  • A join code identifies a room. It is six characters, shared in a group chat, and the invite page lives at /j/CODE. Knowing it lets you add yourself to the room with a nickname and a wishlist. It does not let you read anything about the other people.
  • A personal token identifies one person. It is the secret part of /p/TOKEN. Whoever holds the link is that person: they can edit their wishlist, open their gift box, send anonymous notes and guess their Santa.

The two are generated differently on purpose. The join code is meant to be typed or read aloud, so its alphabet leaves out look-alike characters (no 0, O, 1 or I). The token is not meant to be typed by anyone, so it is 24 random bytes from crypto.getRandomValues, encoded as a 32-character URL-safe string.

export function newToken(): string {
  return base64url(randomBytes(24));
}

export function newJoinCode(length = 6): string {
  return Array.from(randomBytes(length), (b) => CODE_ALPHABET[b % CODE_ALPHABET.length]).join("");
}

Storing only hashes

The token is shown to its owner once, in their link, and then the server keeps only its SHA-256 hash. The participants table has a token_hash column with a unique constraint and no column for the token itself. Looking someone up means hashing the incoming token and querying by hash:

const hash = await hashToken(token);
const me = await db()
  .prepare("SELECT id, room_id, nickname, is_host FROM participants WHERE token_hash = ?")
  .bind(hash)
  .first<ParticipantRow>();
if (!me) return fail(ApiError.NotFound);

Because the token is 192 bits of randomness rather than a human-chosen password, a plain unsalted SHA-256 is enough: there is nothing to guess and nothing to look up in a dictionary. What the hash buys us is that a database export, a stray query result or a debugging session does not hand anyone a working link. Our rule for the code base is simple: never log a token, and never return another person's token. Pages and rooms that have passed their retention date read as not found, and a daily job deletes them.

The host is not special at the access level. The host's token is created when the room is created and works the same way; the host flag only enables host actions such as running the draw.

The server never sends your Santa early

Hashing protects the links. The harder secret is the draw result. Anyone with the page open could in principle read the browser's network traffic, so the only reliable rule is that the data is not in the response at all.

We enforce that by having exactly one function, loadView, build the payload for the room page. Every client component receives a RoomView, a type that contains no tokens, no hashes of anyone but the viewer, and no field for "who is my Santa" before reveal day. Inside the function, the assignments are read, but only three things are derived from them:

  1. the viewer's own receiver, because they need to see whom they give to;
  2. the message thread with that receiver and with their Santa, as an unnamed anonymous side;
  3. two hints for the guessing game on exchange day: how many notes the Santa sent, and the length of the Santa's nickname.

The Santa's name appears only inside the reveal branch, which is built only when the room has reached the reveal phase, the reveal mode allows it, and the viewer has already submitted a guess. Otherwise the payload carries { shown: false }. The full list of pairs is added only when the host chose the mode that shows everyone.

const revealShown =
  phase === Phase.Reveal && room.reveal_mode !== RevealMode.None && myGuess !== "";

Putting this in one place matters more than any clever check. If every page assembled its own response, the next feature would eventually add a field that leaks. With one builder and one type, a review of a new feature is a review of one function.

What this design costs

A link that works as a password has the usual weakness: if someone forwards it, they are you. There is no recovery either. A person who loses the link cannot sign back in with an email, because we have none. We accept that for a game that lasts a few weeks, and we keep the token out of everything that is not the page the owner opened. Writes are POST requests that must come from our own origin, which blocks cross-site form posts. And because the data is deleted 30 days after the exchange date, there is little to lose by the time a lost link would matter.
