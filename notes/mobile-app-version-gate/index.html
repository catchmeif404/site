A version gate for old mobile app builds

Published 2026-11-24 · catchmeif404

A web page updates the next time someone loads it. A mobile app does not: people keep running whatever build they installed, and the backend has to keep answering them. When an API change breaks an old build, or when we simply want people to move to a new release, the server needs a way to say so. In figdex, the figure collection app, the backend serves two version numbers per platform for this: a minimum and a latest.

Two values, two different effects

The app asks the backend for its release configuration at GET /v1/app/config. The response carries a minVersion and a latestVersion for the platform, plus the store URL. The app compares its own version against both.

ValueApp older than itWhat the user sees
minVersionBlockedThe app stops on an update screen, and the server also refuses its API calls with HTTP 426.
latestVersionStill worksA notice that can be dismissed.

Latest is an invitation. Minimum is a requirement. They are separate on purpose, so that we can nudge everyone toward a new release for weeks without cutting anyone off, and keep the hard stop for the day an old build can no longer work.

The server enforces it too

An app that skips its config screen, whether it was left open for days or the config request failed, must not slip through. So a backend filter checks every request under /v1/. The app sends its version in an X-App-Version header and its platform in X-App-Platform. If the version is lower than that platform's minimum, the filter answers 426 UPGRADE_REQUIRED. The config endpoint itself is exempt so the app can still read the message. Requests without a version header, such as a web build or curl, are not version-checked.

The same filter handles maintenance mode, which answers 503 MAINTENANCE. That is a separate switch from the version gate.

Two details keep the gate from hurting people by mistake. Only the version name is compared, such as 1.2.3 from the app's pubspec version, and the build number after the plus sign is ignored. And a version that cannot be parsed is treated as unknown: the app does not compare it and does not block, so a bad config cannot lock everyone out.

Why latest waits for the store

The rule written next to the configuration is plain: after a release, force an update only after confirming that the new build is open in the store. Raising the minimum first blocks people who have nothing to download. The same reasoning applies to latest. A notice that says "a new version is available" is a promise, and if the store has not made the build available yet, tapping through leads to the old version.

For Android this is automated. After the release workflow uploads the app to Google Play, it asks the Play Developer API whether the version code now shows on the internal track, waiting up to 20 minutes. Only when it does, the workflow calls an internal endpoint, POST /v1/internal/app-release/latest, to raise latestVersion. That step runs only if a release key is configured. If the build is not found in time, or no key exists, the workflow leaves a notice and skips the step without failing, and a person raises the value by hand in the admin screen. iOS goes through the same admin screen.

The endpoint is conservative. Sending the current value changes nothing. Sending a lower one is rejected with a 409, so latest only moves forward. It also rewrites only the latest value, so it cannot undo a minimum version or maintenance setting that an admin just saved. Each change is written to the audit log.

Raising the minimum is a later, separate decision

The automatic step never touches minVersion. It shows only the dismissible notice. A forced update is a deliberate act, done after the new build is confirmed in the store, and it is the one that actually closes the door on old builds. Keeping the two values apart means the routine part of a release cannot, by itself, lock anyone out.

The initial values come from environment variables, FIGDEX_ANDROID_MIN_VERSION and its latest, iOS and store-URL counterparts, defaulting to 1.0.0. They only apply until an admin saves the settings once. After that, the stored values win.
