Rate limits without storing IP addresses

Published 2026-11-24 · catchmeif404

A site with no accounts has no obvious handle for abuse. Anyone can create rooms, villages or letters as fast as a script can send requests, and there is no user to ban. The usual answer is to limit by IP address, but that means keeping IP addresses, and we would rather not keep data about visitors that we cannot justify. This note covers what we did instead for SantaPick, and where we chose not to limit at all.

Hourly counters keyed by a hash

Creation endpoints (rooms, decorated rooms, couple quizzes, villages, joining a village, saving a test result) are capped per network per hour. The server never stores the address. It hashes it first, with the same SHA-256 helper used for tokens, over the string ip:<address>, and stores that:

export const ipHashOf = (request: Request) =>
  hashToken(`ip:${request.headers.get("cf-connecting-ip") ?? "local"}`);

The counter table has one row per bucket, IP hash and UTC hour:

CREATE TABLE rate_limits (
  bucket TEXT NOT NULL,
  ip_hash TEXT NOT NULL,
  hour TEXT NOT NULL,   -- YYYY-MM-DDTHH (UTC)
  n INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (bucket, ip_hash, hour)
);

The limits are numbers in one constants object: 30 new rooms per hour, 30 decorated rooms, 30 couple quizzes, 20 villages, 60 village joins, 60 test results. They are meant to stop scripts, not to inconvenience a household or an office behind one address.

One statement, no race

The naive version reads the count, compares it to the cap, then writes the new count. Two requests arriving together both read 29 and both pass. We avoid that by making the check and the increment the same statement:

INSERT INTO rate_limits (bucket, ip_hash, hour, n) VALUES (?, ?, ?, 1)
ON CONFLICT (bucket, ip_hash, hour) DO UPDATE SET n = n + 1 WHERE n < ?

The first request of an hour inserts a row with 1. Later ones hit the conflict and update the row, but only while n is still below the cap. When the cap is reached, the WHERE makes the update touch nothing. The code then reads the number of changed rows from the result: one means the request was counted and may continue, zero means refuse with a 429. Because the database serialises that single statement, concurrent requests cannot both squeeze in under the limit.

Device keys for the rest

Some limits are about a device, not a network. The browser makes a random key and keeps it locally. The server never stores that key either, only its hash. Villages and houses use it to enforce one of each per device, bells (our play money, never sold) keep a wallet under the key's hash, and a deco letter is limited to one per visitor per room by hashing the room id together with the key.

These keys are easy to discard, so they are a convenience limit rather than a security boundary, and we pair them with a network limit where it matters. For example, the sponsor-card reward is capped at three a day with a 15-second minimum play time checked on the server, and the number of new wallets per network per day is capped as well. We set that last cap loosely, because mobile networks share addresses between many people.

What gets deleted, and when

The counter rows are useful only for the hour they cover. The daily job at 03:00 KST deletes rate-limit rows from before today, along with expired rooms, villages and everything inside them. Rooms themselves are kept until 30 days after their exchange date. A few IP hashes live longer than the counters, attached to rows that need them: letters and letter reports in decorated rooms carry one, so the per-network letter cap and one-report-per-network rule can work, and wallets carry one for the new-wallet cap. They go when the row goes.

The counter that has no limit

The visit counter is the exception. A visit is one tab's first page load, and the endpoint adds one to a per-day total. It is a POST that must come from our own origin, and that is the only check. We deliberately did not add a per-IP limit, because limiting visits would mean writing an IP hash for every visitor, including people who never create anything, and the privacy policy does not cover that. The cost of the choice is that a script can inflate the number. We accept that: the figure is for our own sense of scale, nothing depends on it, and a number we can shrug at is cheaper than a log of everyone who looked at the page.
