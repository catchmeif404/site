How the Secret Santa draw works

Published 2026-11-24 · catchmeif404

A Secret Santa draw sounds like shuffling names, but the requirements add up quickly. Everyone gives to exactly one person and receives from exactly one person. Nobody draws themselves. The host can mark pairs of people who must not draw each other, such as a couple or two people who already know each other's tastes. And if the rules cannot be satisfied, the host needs to hear that instead of waiting on a request that never ends. The whole thing is one pure function, drawPairs, in src/lib/draw.ts.

Inputs and rules

The function takes a list of participant ids, a list of excluded pairs, and an optional random number generator. In production we pass one built on crypto.getRandomValues; in tests the default is fine. It returns either a list of giver, receiver pairs or { ok: false }.

Exclusions are symmetric: the host says "A and B must not meet", and that bans both A giving to B and B giving to A. We store each pair under a key built from the two ids in sorted order, so a lookup works in either direction.

function key(a: string, b: string): string {
  return a < b ? `${a}|${b}` : `${b}|${a}`;
}
const allowed = (g: string, r: string) => g !== r && !banned.has(key(g, r));

A room needs at least three people to be drawn (the room limits are 3 to 50), and the function itself returns failure for fewer than two.

First try: one big cycle

The first strategy is to shuffle everyone into a line and have each person give to the next, with the last person giving to the first. That produces a single cycle: A gives to B, B to C, and so on back to A. A single cycle is a valid draw whenever every neighbouring pair is allowed, and it has a useful property for a game about guessing. With several small loops, someone who works out that they and their receiver swapped gifts, or that a three-person loop closed, learns far more than they should. One long cycle gives no such shortcut.

We try this up to 400 times. A random cycle fails only if some neighbouring pair is banned, so rooms with few or no exclusions usually succeed early.

Detecting impossible rooms

If 400 shuffles fail, the setup is either tight or impossible. We check the cheap impossible cases first. If anyone has nobody they are allowed to give to, or nobody allowed to give to them, no draw exists:

for (const id of ids) {
  if (!ids.some((o) => allowed(id, o)) || !ids.some((o) => allowed(o, id))) return { ok: false };
}

The simplest example in the tests is three people where the first is excluded from both others. The test for a person excluded from everyone, in a room of fourteen, also asserts that the answer comes back in under 200 milliseconds.

That check does not catch every impossible input, because a conflict can involve several people at once even when each one has an option on their own. For the rest we fall back to a backtracking search that allows any valid assignment, not just a single cycle. It orders givers by how few options they have, so the most constrained person is placed first, and tries receivers in random order. It also counts nodes explored and gives up after 20,000, so a hard or impossible input cannot hang the request.

That limit is a deliberate trade. If the search stops at the cap we report the draw as impossible, even though in some very tight setups a solution could exist that we did not reach. In both cases the host gets a draw-impossible error and the next step is the same: change the exclusions.

Committing the result safely

The draw function only computes pairs. Writing them is a separate step that must not be fooled by a concurrent change. runDraw writes everything in one batch: the first statement closes the room only if it is still open and still has exactly the number of people we drew for, and each assignment insert runs only if the previous statement changed a row (SQLite's changes()). If someone joins between reading the participants and writing the pairs, the close changes nothing, and so nothing else is written. The host gets a "room closed" answer and can try again.

How it is tested

The tests in draw.test.ts run the function many times, since the result is random:

  • 200 runs with eight people check that everyone appears once as giver and once as receiver, and that nobody draws themselves;
  • 200 runs with three exclusions check that no pair appears in either direction;
  • the three-person minimum works;
  • impossible setups return ok: false, including a single person;
  • a person excluded from everyone fails fast;
  • a tight case: on a ring of eight where only neighbours may meet, the only valid draws are the two directions around the ring. A random shuffle rarely lands on one of them, so the backtracking path has to find it. The test asserts it solves this 20 times in a row.

The last test is the one that matters most to us. It is easy to write a draw that works for rooms with no rules and quietly fails for the rooms that need it.
