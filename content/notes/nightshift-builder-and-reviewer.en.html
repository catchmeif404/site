Letting a coding agent work while nobody is watching goes wrong in boring ways. It edits your checkout, it reports success without having written the result anywhere, it dies when the laptop sleeps, or it merges something that touches money. nightshift is the small part around the agents that handles those cases. It is open source under the MIT license, published on npm as @catchmeif404/nightshift, with the source at github.com/catchmeif404/nightshift. The README calls its status early (0.1).

What it is, and what it is not

nightshift is an unattended development queue that runs on your own machine. You put tickets on a board. For each ticket it starts a developer run of a coding agent, by default Claude Code sonnet (Codex is supported too), which builds the change on its own branch. It then starts a separate reviewer run, by default opus, that checks the work. The reviewer fixes small things, sends larger ones back for another round, and stops anything that needs a human.

nightshift writes no code itself. The agents build and review. nightshift picks the next ticket, gives each one its own git worktree, starts and resumes the agent runs, accepts a result only from the file the run must write, sends work back for rework, merges what passed if you allow it, and keeps the ticket up to date. The model that wrote the code is never the one that approves it.

Boards

A board is where tickets live. The README lists these types:

  • local-md, the default: a folder of markdown files in .tickets/.
  • github: GitHub Issues, using nightshift:* labels such as nightshift:ready. Only issues opened by trustedAuthors are picked up, because an issue is a prompt.
  • notion: a Notion database, with property and status names configurable.
  • command: any tracker, through a small executable that implements list, set-status and note, so Linear, Jira or a spreadsheet can act as the board.

From ticket to merged pull request

The quick start is four commands:

npm install -g @catchmeif404/nightshift
nightshift init --repo-path ~/code/my-app
nightshift add "Add a slugify helper" --project my-app
nightshift run

A ticket then moves like this. A worker takes a ready ticket for its project, with one worker per project and a few projects at once. The build stage runs in a fresh worktree and must end by writing one line to a result file: PR <url>, BRANCH <name> or BLOCKED <why>. The review stage runs the tests and writes PASS, REWORK, NEEDS_HUMAN or BLOCKED. On REWORK the builder runs again with the review notes and the reviewer looks once more; maxRework defaults to 1.

On PASS the ticket goes to review for you to merge. With autoMerge on, nightshift merges the pull request itself and the ticket becomes done. autoMerge is off by default. With publish: "pr" the branch is pushed and a pull request is opened; with "branch" the work waits on a local branch such as nightshift/t-1.

Human gates

Some changes should not be merged by a model. humanGates defaults to all five: money, legal, destructive-data, outward-facing and product-direction. When a change touches one, the reviewer answers NEEDS_HUMAN, writes what you must decide, and the ticket goes to blocked. A ticket that changes a price is the example the getting-started guide uses. Separately, gatePaths takes globs such as db/migration/**: if the change touches a matching file, a passing review becomes NEEDS_HUMAN even with autoMerge on.

Why a run survives a bad night

  • Files, not claims. A stage counts as done only when it writes its result file in the expected format. A result it cannot read is set aside and the stage runs again.
  • Cut-off runs resume. Each stage has a fixed session id, so after a reboot the next dispatch resumes the same session. After 3 cut-offs (maxStageTries) the ticket is blocked with the last log line as the reason.
  • Usage limits wait. When the agent reports a limit with a reset time, nightshift does not count it as a try and resumes after the reset.
  • Your checkout is untouched. Every ticket works in its own worktree and branch.

The README reports one measurement from our own use: its bash predecessor took 225 tickets through build and review in the first 12 days, and 84% passed review on the first round. That pass is the AI reviewer's verdict, not a human's, and the README says so.

It needs Node 20 or newer, git and a signed-in Claude Code CLI. Because it runs agents that can edit files and run commands, the README advises a machine and repositories where that is acceptable, autoMerge off until you trust it, and a short trustedAuthors list.
