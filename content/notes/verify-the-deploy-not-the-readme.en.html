The deployment notes for the catchmeif404.com site said that it redeploys through Cloudflare Pages' git integration whenever main changes. That sentence was written as a fact. It was not one. The GitHub-to-Cloudflare-Pages connection did not exist until 2026-09-07.

What was actually happening

The site is plain static HTML, CSS and JavaScript, with no build step. Before the connection existed, every deploy had been done by hand with the wrangler CLI. Because the README described the git integration as already working, pushing to main felt like deploying. It did nothing. The commit landed on GitHub, the live site stayed as it was, and nothing failed or complained, since nothing was listening for the push.

That is what makes this class of problem expensive. A deploy that fails loudly gets fixed the same day. A deploy that silently does not happen leaves you looking at old behavior and doubting the code you just wrote, while the real cause is a missing link between two services.

What the documentation could not tell us

The text said the integration existed, and the repository gave no way to contradict it. A README can describe what a system is supposed to do. It cannot show what the provider's side is configured to do, because that configuration lives in a dashboard the repository never sees. Reading the document again would not have found the gap. Only an action with an observable result could: push a change and look at the live site.

The lesson we took is narrower than "write better docs". Documentation of a deployment is a claim, and a claim about another system needs to be checked against that system. So we check a connection like this by pushing something and watching it appear, instead of trusting a README's claim that it works. The same applies to a note we wrote ourselves a month ago.

The habit we took from it

We stopped treating a document, a toggle or a green build as proof of a deploy. The rule now has three parts:

  1. Verify a new connection by using it. Push something small and check that it shows up on the live URL. Do this the first time a git integration is set up, and again whenever someone says it already works.
  2. A successful build is not a deployment. A build only shows that code compiled. After a deploy we check the live URL or the provider's deployment record, and write down the actual result in the project's status document. We do not infer a deployment from a green build.
  3. Ask the provider what started the deploy. The same mistake appeared on the Railway side. We believed Automatic Deploy was off, but every push to main still started a competing deploy. We only saw it by reading latestDeployment.meta from railway status --json and noticing that the reason was a branch push, not a tag.

What a verification looks like

The check should be cheap enough that nobody skips it, and it should end in something you can see.

For a static site, it can be as small as checking that a change is visible at the public address:

# after pushing a visible change
curl -s https://catchmeif404.com/ | grep "the text you just changed"

For a Railway service it means reading the deployment record and then calling the service. The record tells you which commit or tag started the deploy, and a request to a real endpoint tells you whether the new version is the one answering. Neither of them replaces the other: the record can say deployed while the proxy still points at the wrong port, and a working endpoint can be an older instance.

Where this fits with tag-triggered deploys

Our production deploys are driven by vX.Y.Z tags, as described in Deploy on tags, not on main. A tag-based setup has more moving parts than a plain push: a workflow trigger, a provider token, a service name, and sometimes a variable that must be applied. Each of those can be misconfigured without any error on the commit. The Railway checklist lists the ones that have hurt us.

The site itself still deploys from pushes to main through the Cloudflare Pages connection, and moving it to a tag-driven deploy remains a separate job. In the meantime the connection works because we pushed a change and watched it appear, not because a document says so.
