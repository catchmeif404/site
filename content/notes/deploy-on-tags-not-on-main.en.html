For a while, merging to main and deploying to production were the same action in some of our repos. That is convenient until you are iterating on an unrelated feature and every push replaces what users are running. We moved to a rule where production changes only when a version tag is pushed.

The rule

Regular commits and pushes to main do not trigger a production deploy. A deploy happens only when a tag of the form vX.Y.Z (semver, for example v1.0.0) is pushed. The deploy workflows listen for tags, plus a manual trigger for reruns:

on:
  push:
    tags: ['v*']
  workflow_dispatch:

Cutting a release is two commands, run once main is in the state you want shipped:

git tag v1.0.0
git push origin v1.0.0

One shared tag for frontend and backend

Our default is one shared tag per repository that triggers the workflow of every deployable service. In AWS CostPilot (repo aws-cost-calculator) the frontend deploys to Cloudflare Workers and the backend deploys to Railway. Both workflows, deploy-frontend.yml and deploy-backend.yml, are triggered by the same v* tag, so the two halves of a release always come from the same commit.

The alternative is a prefixed tag per service, such as frontend-v1.0.0 or worker-v1.0.0. We only reach for that when services genuinely need to release independently of each other. For a frontend and a backend that share an API contract, one tag is simpler and removes a class of version-skew questions.

What changed in practice

The backend of AWS CostPilot used to deploy on every push to main through Railway's own GitHub integration. We turned that off in the Railway dashboard and replaced it with the tag-triggered workflow, which runs railway up through the Railway CLI. That workflow needs a RAILWAY_TOKEN repository secret, which is a Railway project token.

Day to day this means:

  • Merging a pull request is safe at any time. It changes main, not production.
  • Work in progress can sit on main across several merges and be shipped later as one release.
  • A deploy has a name. The tag tells you which commit is live, and rerunning an older tag through the manual trigger is a way back to a previous state.
  • The moment of shipping is a deliberate step, not a side effect of a merge.

One practical effect is on how we write commit messages and pull requests. Because nothing ships on merge, a half-finished change can land in a small step without anyone worrying that it is already live. The decision about whether the current state of main is good enough to ship is made once, at tag time, by looking at main as a whole instead of at each pull request in isolation. That is also when we look at database migrations, since a release with a migration is the one we most want to take deliberately.

Two places this did not apply cleanly

The first is the static site for catchmeif404.com. It deploys through Cloudflare Pages' own git integration and redeploys on every push to main. There is no build command and no output directory, because it is plain HTML, CSS and JavaScript. Moving it to an Actions-driven, tag-triggered deploy is a separate migration that we have not done. The tag rule describes where we are heading for every repo, not a claim that every repo is already there.

The second is that turning off a deploy mechanism is easy to believe and hard to verify. On the backend we thought Railway's automatic deploy was off while every push to main kept starting a second deploy that raced the tag workflow. We cover how to check for that in the Railway checklist.

Migrating an existing repo

When we touch a repo that still deploys from main, the steps are the same each time:

  1. Change the workflow trigger from push: branches: [main] to push: tags: ['v*'] and add workflow_dispatch.
  2. Turn off the provider's own git-triggered deploy, so there is only one path to production.
  3. Check that it is really off, not just that you clicked the toggle.
  4. Push a tag, watch the workflow, and open the live URL to confirm what is running.

The last step matters as much as the first three. A tag push that produces a green workflow is evidence that a workflow ran, not that the service changed. We wrote about that separately in Verify the deploy, not the README.
