마스크맨 온라인 대전에서 두 브라우저는 위치나 체력을 보내지 않아요. 프레임마다 어떤 버튼을 눌렀는지만 보내요. 각자 그 입력을 자기 쪽 게임에 넣어서 돌리기 때문에, 두 쪽이 정확히 같은 숫자를 계산해야만 같은 싸움이 돼요. 이 글의 내용은 전부 거기서 나와요.

시뮬레이션의 모양

게임 규칙은 전부 src/sim/에 있고, 여기서는 DOM을 건드리지 않아요. 진입점은 함수 하나예요.

step(world, [p1Bits, p2Bits])

한 번 부르면 월드가 1프레임, 초당 60프레임 기준으로 한 칸 나아가요. 입력은 플레이어마다 정수 하나이고, 값이 2의 거듭제곱인 버튼 enum으로 만들어요.

export enum Btn {
  Left = 1, Right = 2, Up = 4, Down = 8,
  Attack = 16, Grab = 32,
  SkillA = 64, SkillB = 128,
  Mask = 256, Super = 512,
}

그래서 한 사람의 한 프레임 입력은 1,024 미만의 숫자 하나예요. 여러 프레임을 한 메시지로 묶어 보내기에 충분히 작아요. 렌더러, 소리, 메뉴는 월드를 읽기만 하고 바꾸지 않아요. 실시간 루프는 시뮬레이션을 1000/60ms 단위로 돌리기 때문에, 화면이 얼마나 빨리 그려지는지가 싸움 결과에 영향을 주지 않아요.

코드가 따르는 규칙

저장소의 에이전트 가이드에 규칙이 그대로 적혀 있어요. 시뮬레이션은 브라우저가 달라도 결정론적이어야 해요. src/sim/ 안에서는 Math.random도, Math.sin, Math.cos, Math.hypot 같은 엔진마다 다를 수 있는 수학 함수도, 실제 시계도 쓰지 않아요. 실제로는 이렇게 지켜요.

  • 난수는 상태가 데이터 안에 들어 있는 시드 생성기에서 나와요. CPU 플레이어는 필드에 작은 선형 합동 생성기를 두고 Math.imul과 부호 없는 시프트로 갱신해요. 로그라이크 한 판도 자기 시드 생성기를 판 객체 안에 가지고 있어요.
  • 시간은 프레임 카운터예요. 쿨다운, 히트스톱, 라운드 타이머 모두 프레임 수로 세요.
  • 언어 표준이 결과를 정확히 정해 둔 함수는 괜찮아요. Math.abs, Math.min, Math.max, Math.floor, Math.imul 같은 것들이에요. 삼각함수처럼 엔진이 마지막 자리에서 다를 수 있는 함수는 안 돼요. 위치가 1비트만 달라도 그 차이가 커져서 다른 싸움이 되기 때문이에요.
  • 규칙은 키보드에 묻지 않고 파이터에 저장된 상태를 읽어요. 최근에 누른 방향 기록도 그 상태에 들어 있어요. 2 3 6 같은 방향 입력(아래, 아래 앞, 앞) 커맨드 기술은 이 기록으로 판정하니까 양쪽이 같이 계산하는 상태의 일부예요.

이 글을 쓰다가 발견한 점도 있어요. 용암 스테이지의 위험 지대 위치는 사인 함수를 쓰는 도우미 hash01로 정해요. 규칙이 금지하는 종류의 함수예요. 이것 때문에 생긴 어긋남을 본 적은 없지만, 정수 연산으로 바꾸는 게 맞아요. 규칙은 코드가 지킬 때만 의미가 있어요.

플레이 중에 어긋남을 잡아내요

규칙만으로는 증명이 안 되니 게임이 직접 확인해요. 120프레임마다, 즉 2초마다 각자 월드의 해시를 계산해서 상대에게 보내요. 해시에는 프레임 번호, 파이터별 위치·체력·상태·가드 체력, 그리고 투사체 수와 라운드 타이머가 섞여요.

h = Math.imul(h ^ Math.round(v * 16), 2654435761) >>> 0;

값은 1/16 단위로 반올림해서 섞어요. 상대 해시가 도착했는데 같은 프레임의 내 해시와 다르면, 링크가 desync 플래그를 켜고 프레임 번호를 로그에 남겨요. 일어난 일을 알려 주는 용도일 뿐, 경기를 다시 맞춰 주는 장치는 없어요. 해시는 상태의 일부만 보기 때문에, 포함되지 않은 값이 어긋나도 그 차이가 포함된 값에 닿을 때까지는 못 잡을 수 있어요.

테스트는 이렇게 확인해요

가장 단순한 테스트가 가장 중요해요. 월드를 만들고, CPU 둘에게 고정 시드를 주고, 2,400프레임(게임 시간 40초)을 돌린 뒤 파이터, 매치, 투사체를 JSON으로 직렬화해요. 이걸 두 번 해서 문자열이 같은지 봐요.

expect(play()).toBe(play());

난수, 시간, 남아 있는 모듈 상태를 읽는 코드는 이 테스트에 걸려요. 하지만 두 번 모두 같은 엔진에서 돌기 때문에, 서로 다른 브라우저 사이의 차이는 못 잡아요. 그 부분은 통합 테스트가 있는데, 개발 서버 주소를 주었을 때만 돌아요. 헤드리스 클라이언트 둘이 실제 방 서버를 거쳐 한 경기를 끝까지 하고 서로 일치하는지 확인해요.

바뀌면 안 되는 형식을 고정하는 테스트도 있어요. 가면, 스킬, 특성 같은 저장용 enum은 숫자로 저장되니까 새 항목은 맨 뒤에만 넣을 수 있고, 기존 항목이 움직이면 테스트가 실패해요.

여전히 깨지는 지점

흔한 실패는 새 기능이 월드 밖의 값을 슬쩍 읽을 때예요. 시각 효과에 쓰려던 무작위 선택이 피해량까지 바꾸거나, 객체 순회 순서에 기대는 조회가 그런 예예요. 우리가 의존하는 건 짧은 규칙 목록, 반복 실행 테스트, 주기적인 해시예요. 전체 상태를 비교하는 것보다는 얇은 방어선이에요.
