계정이 없는 사이트에는 악용을 막을 손잡이가 마땅치 않아요. 누구나 스크립트가 보내는 속도만큼 방이나 마을, 편지를 만들 수 있고, 차단할 사용자도 없어요. 보통은 IP 주소로 제한하지만 그러려면 IP 주소를 보관해야 해요. 방문자에 대한 정보를 이유 없이 갖고 싶지는 않았어요. 이 글은 산타픽에서 대신 한 일과, 일부러 제한을 두지 않은 곳을 다뤄요.

해시를 키로 쓰는 시간당 카운터

만들기 요청(방, 꾸민 방, 커플 퀴즈, 마을, 마을 입장, 테스트 결과 저장)은 네트워크별로 시간당 횟수를 제한해요. 서버는 주소 자체를 저장하지 않아요. 토큰에 쓰는 것과 같은 SHA-256 함수로 ip:<주소> 문자열을 해시해서 그 값만 저장해요.

export const ipHashOf = (request: Request) =>
  hashToken(`ip:${request.headers.get("cf-connecting-ip") ?? "local"}`);

카운터 테이블은 버킷, IP 해시, UTC 시각 단위로 한 행이에요.

CREATE TABLE rate_limits (
  bucket TEXT NOT NULL,
  ip_hash TEXT NOT NULL,
  hour TEXT NOT NULL,   -- YYYY-MM-DDTHH (UTC)
  n INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (bucket, ip_hash, hour)
);

한도는 상수 객체 하나에 모여 있어요. 시간당 방 30개, 꾸민 방 30개, 커플 퀴즈 30개, 마을 20개, 마을 입장 60번, 테스트 결과 60번이에요. 스크립트를 막으려는 숫자이지, 한 집이나 한 사무실이 주소 하나를 같이 써서 불편하게 하려는 숫자가 아니에요.

한 문장이라 경합이 없어요

단순한 방식은 횟수를 읽고, 한도와 비교하고, 새 횟수를 쓰는 거예요. 그러면 동시에 들어온 두 요청이 둘 다 29를 읽고 둘 다 통과해요. 그래서 확인과 증가를 같은 문장으로 합쳤어요.

INSERT INTO rate_limits (bucket, ip_hash, hour, n) VALUES (?, ?, ?, 1)
ON CONFLICT (bucket, ip_hash, hour) DO UPDATE SET n = n + 1 WHERE n < ?

그 시간의 첫 요청은 1이 든 행을 넣어요. 다음 요청부터는 충돌이 나서 행을 갱신하는데, n이 한도보다 작을 때만 갱신해요. 한도에 닿으면 WHERE 때문에 아무 행도 바뀌지 않아요. 코드는 결과에서 바뀐 행 수를 읽어서, 1이면 세어졌으니 계속 진행하고 0이면 429로 거절해요. 데이터베이스가 이 한 문장을 순서대로 처리하니까 동시 요청이 한도 아래로 함께 끼어들 수 없어요.

나머지는 기기 키로 해요

어떤 제한은 네트워크가 아니라 기기 기준이에요. 브라우저가 무작위 키를 만들어 로컬에 두고, 서버는 그 키도 저장하지 않고 해시만 저장해요. 마을과 집은 이 키로 기기당 하나씩만 만들게 하고, 벨(판매하지 않는 놀이용 재화)은 키의 해시 아래 지갑을 두며, 꾸민 방의 편지는 방 id와 키를 함께 해시해서 방문자당 방마다 한 통으로 제한해요.

이런 키는 버리기 쉬워서 보안 경계가 아니라 편의를 위한 제한이에요. 중요한 곳에서는 네트워크 제한과 함께 써요. 예를 들어 후원 카드 보상은 하루 세 번까지이고 최소 15초 재생을 서버에서 확인하며, 네트워크당 하루에 새로 만드는 지갑 수도 제한해요. 이 마지막 한도는 일부러 느슨하게 잡았어요. 모바일 망은 여러 사람이 주소를 나눠 쓰기 때문이에요.

무엇을 언제 지우나요

카운터 행은 그 시간 동안만 쓸모가 있어요. 매일 03:00(KST)에 도는 작업이 오늘보다 앞선 rate-limit 행을, 만료된 방과 마을 및 그 안의 모든 데이터와 함께 지워요. 방은 교환일 30일 뒤까지 보관해요. 일부 IP 해시는 카운터보다 오래 남는데, 그 해시가 필요한 행에 붙어 있어서예요. 꾸민 방의 편지와 편지 신고는 네트워크별 편지 한도와 신고 중복 방지를 위해 하나씩 갖고, 지갑은 새 지갑 한도를 위해 하나를 가져요. 행이 지워질 때 함께 사라져요.

제한이 없는 카운터

방문 카운터는 예외예요. 방문은 한 탭의 첫 페이지 로드이고, 이 엔드포인트는 하루 합계에 1을 더해요. 우리 사이트에서 보낸 POST여야 한다는 것이 유일한 검사예요. IP별 제한은 일부러 넣지 않았어요. 방문을 제한하려면 아무것도 만들지 않은 사람까지 포함해 모든 방문자의 IP 해시를 써야 하는데, 개인정보처리방침이 그걸 다루지 않기 때문이에요. 대가는 스크립트가 숫자를 부풀릴 수 있다는 점이에요. 이건 받아들였어요. 이 숫자는 우리가 규모를 가늠하는 용도이고 아무것도 이 값에 기대지 않아요. 웃어넘길 수 있는 숫자가, 페이지를 본 모든 사람의 기록보다 싸요.
