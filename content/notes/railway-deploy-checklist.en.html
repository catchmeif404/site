We deploy backends to Railway with a tag-triggered GitHub Actions workflow that runs railway up. Most of the time lost on that setup came from five small mismatches, two of which bit us more than once. This is the checklist we use for a new service, or for one that deploys but returns 502 or cannot find its Postgres.

1. The service name must match --service exactly

Symptom: the workflow cannot find the service, or deploys to something other than what you expected.

Cause: Railway does not necessarily name a service after the repository or folder. The backend service of aws-cost-calculator is literally named aws-cost-calculator, not backend.

Fix: read the name in the dashboard and put that exact string in the workflow.

railway up --service aws-cost-calculator

2. Run railway up from the repo root

Symptom: the build fails with "Root directory '/backend' was not found in the deployed source", or with "Railpack could not determine how to build the app".

Cause: a service can be deployed two ways, by the workflow and by the dashboard or GitHub integration (a manual Deploy click, or Automatic Deploy if it is still on). They must upload the same shape of source, or the Root Directory setting can be right for only one of them:

  • railway up run from inside backend/ uploads a snapshot already scoped to that folder. Root Directory backend then scopes twice and fails.
  • Root Directory left empty with the dashboard path makes Railpack scan the repo root, find no buildable entry point, and fail.
  • railway up run from the repo root uploads the whole repository, the same as the dashboard path, so Root Directory backend resolves correctly for both.

Fix: no working-directory: backend and no defaults.run.working-directory on the deploy step, and Root Directory set to backend. If this error comes back, check whether the workflow has drifted to running from inside backend/ before touching the Root Directory setting.

3. The networking port must match what the app binds to

Symptom: every request returns 502 "Application failed to respond", although the logs show the app booted.

Cause: Railway injects its own PORT variable, often 8080, and the app binds to that, whatever the Dockerfile's EXPOSE says. If the generated domain points at a different port, the proxy cannot reach the app.

Fix: find the line the framework logs at startup (for Spring Boot, "Tomcat initialized with port ___") and set the domain's target port to that number. Alternatively set PORT explicitly as a variable to force the value.

4. Turn off Automatic Deploy, then verify that it is off

Symptom: random failures and stale-looking instances while you iterate on something unrelated. The deploy mechanism looks flaky.

Cause: we believed Automatic Deploy (Settings, Source) was off. It was not. Every push to main started a second deploy through Railway's GitHub integration, racing the tag-triggered railway up workflow. It cost a long debugging session on aws-cost-calculator.

Fix and check: turn it off, then ask Railway what actually started the last deployment:

railway status --json

Look at a service's latestDeployment.meta. If reason is "deploy" and it carries a repo and commitHash matching a recent branch push rather than a tag, Automatic Deploy is still firing.

5. A new variable can stay unapplied until a dashboard deploy

Symptom: you add a variable, re-run the workflow several times, and the app still sees an empty value.

Cause: we added ADMIN_METRICS_API_KEY and re-ran the tag-triggered railway up workflow repeatedly. A temporary debug log that printed only the value's length confirmed the variable was set to a real value in Railway while the app saw "". Only an explicit manual Deploy click in the Railway dashboard applied it. Every CLI-triggered redeploy after that worked.

Fix: after adding or changing a variable, click Deploy in the dashboard once. After that it is safe to rely on CLI redeploys again. When you debug a variable like this, log its length, never its value.

Order of checks

When a service deploys but does not answer, we go in this order: the service name, the source shape and Root Directory, the port, then whether a second deploy is running, and last the variables. The first four are configuration that can be read in the dashboard or from railway status --json, so they are quick to rule out. For the tag-triggered setup these checks sit behind, see Deploy on tags, not on main.
